# APIMatic integration evidence

## Installed and read during implementation

On November 5, 2026 (Asia/Kolkata), `context-plugins` CLI 0.12.0 installed PayPal and Twilio Context Plugins **0.4.1** into Codex using:

```
CP_TELEMETRY=off npx context-plugins install paypal --targets codex -y
CP_TELEMETRY=off npx context-plugins install twilio --targets codex -y
```

Both installations succeeded. The installer said to start a new session for automatic plugin loading. Instead of claiming automatic tool activation, the current session read installed plugin skill files directly and fetched the published SDK maps and operation pages. No session restart or hidden context activation is claimed.

## SDKs actually used and differences

**PayPal:** official `@paypal/paypal-server-sdk` **2.5.0**, generated by APIMATIC v3.0 (verified source header in installed controllers/configuration/models). Its published npm package provides `Client`, `Environment.Sandbox`, `OrdersController`, and `PaymentsController`. Exact signatures and camelCase property names were checked against installed source. The Context Plugin describes a separate Git-source `paypal` package whose spellings (`payPalRequestId`, `PaypalClient`) differ. We deliberately did not install or claim use of that unpublished package. `paypal-plan.md` records the actual bridge and contract sheet.

**Twilio:** official `twilio` **6.2.0**, rather than the plugin's separate `twilio-sdk` Git-source package, because the official supported Node SDK provides TwiML generation and request signature validation alongside typed messaging. APIMatic's generated wire contracts were cross-checked against its typed `messages.create`. We do not claim this Twilio package was generated by APIMatic.

**REST exception:** PayPal's generated Orders/Payments controllers do not expose notification signature verification. A narrow server-only adapter implements `/v1/notifications/verify-webhook-signature` against official PayPal specifications and uses a bounded cached OAuth grant. No broad untyped REST payment implementation replaces generated controllers.

## Resulting files and behavior

`src/server/integrations/paypal.ts`: explicit sandbox auth, typed create/capture/get/refund controller calls, bounded timeout, SDK retry suppression, error translation, webhook REST exception. `src/server/payments.ts`: durable unique claims before provider writes, stable request keys, exact obligation checks, unknown-result readback, capture/refund persistence. `src/server/integrations/twilio.ts`: typed outbound adapter, vendor signature validator, TwiML. `src/server/messaging.ts`: paired opt-in, window limits, shared conversation service. `src/app/api/[...path]/route.ts`: signature and account checks, dedup inbox, replay boundary and delivery status.

The plugin's automatic per-call idempotency header is insufficient for application retries. We persisted the logical operation identity before the request and set the API-specific PayPal-Request-Id. Timeout/decode ambiguity is never labeled paid or treated as a new independent attempt. 401/403 are integration faults, quota errors are service unavailable, and raw credential-bearing SDK messages are not returned or logged.

## Verification evidence

Strict compilation verifies actual SDK models and signatures. Vitest tests assert a durable claim exists **inside** a stubbed provider create call, then simulate dropped answers and assert stable identity and a single UNKNOWN operation. Tests cover duplicate demo capture, refunds, fee shortfalls, tenant/parent ownership and finance-only mappings. Twilio tests verify signature authenticity and body/URL tampering rejection. Read-only provider evidence records PayPal OAuth 200 and Twilio account 200. Financial transactions and public WhatsApp delivery remain unverified. No sandbox-verification evidence is fabricated.

## Financial closure pass

The installed PayPal Context Plugin's model guidance was read again, including optional versus nullable fields and checking the actual installed SDK source before mapping responses. Its getting-started identity warning remained applicable: its `paypal` package 2.29 is a different package from the official installed `@paypal/paypal-server-sdk` 2.5.0. No package replacement or automatic plugin activation is claimed.

The actual APIMatic-generated installed `capturedPayment.ts`, `sellerReceivableBreakdown.ts`, `refund.ts` and `refundRequest.ts` confirmed optional receivable/fee fields, string update timestamps, refund amount and `customId`. That inspection directly changed fee handling and lost-refund recovery. Typed controller contracts supply dedicated UUID PayPal request IDs, explicit USD partial refund amounts, local refund custom IDs and independent GET verification. PayPal's official idempotency guidance also exposed why a 36-character UUID plus `-capture` is too long for the documented 38-byte recommendation: new capture keys are separate durable UUIDs. No blind retry is inferred from SDK idempotency support.

The complete-event webhook fix follows PayPal's official postback-verification contract; the notification endpoint remains a narrow REST exception. Two-process PostgreSQL failure tests use a local fake provider and do not establish PayPal capture/refund verification. See `financial-concurrency-evidence.json` for six independently competing process scenarios.
