# Security and privacy

This is a sample-data hackathon MVP, not a production school information system.

The hosted sandbox is public at https://classequity.onrender.com. Its freely accessible demo accounts are confined to a read-only canonical sample dataset on the server with browser-local interactive simulations (`sessionStorage`, cleared on sign-out). Every server-side write route and demo-school invitation redemption in `demo` mode fails closed with HTTP `403 DEMO_READ_ONLY` (and unsupported HTTP methods return `405`), while read projections filter historical demo drift non-destructively so multiple judges see identical canonical figures without database writes. Public demo rate limits are isolated per authenticated session cookie via hashed in-memory session bindings alongside shared anti-abuse ceilings. `HOSTED_RESTRICT_PUBLIC_AI=true` restricts cloud Gemini tools to password-protected sandbox roles; public parent assistance uses grounded local responses without calling Gemini or writing assessment rows. Demo accounts cannot switch into sandbox membership or its financial operations, and restricted `sandbox` workflows retain full persistence and PayPal Sandbox controls unchanged. Production payment mode remains unavailable. The hosted phase did not provision Twilio credentials or copy the client Studio trial without confirmed public-use scope. A later local outbound Twilio Sandbox delivery was independently confirmed; genuine hosted inbound/status callbacks remain unverified.

Build release preflight uses a read-only transaction against the existing dedicated database. Startup/restart never migrates or seeds. HTTPS readiness checks database connectivity and returns no private values. Private environment handoff and PostgreSQL backup artifacts are ignored and restricted locally; both the pre-deployment and refreshed archives passed an isolated PostgreSQL 17 restore. The existing database external IP allowlist remains broad, and shared-password sandbox identity remains a hackathon limitation. This is not a production security certification.

Implemented: opaque random database-backed 8-hour sessions, hashed tokens at rest, HttpOnly/SameSite=Lax cookies and Secure on configured HTTPS; exact-origin CSRF enforcement on browser mutations; PostgreSQL tenant/object checks; separate finance role for individual aid records; parent ownership checks; Zod input limits; serialized trip freeze/registration via row locks; immutable financial obligations; unique logical payment/refund identities; provider signature verification and webhook inbox deduplication; durable per-hour request quotas; max-size and file-magic validation for quote uploads; no uploaded document persistence; no raw provider secret errors in UI/logs; CSV formula escaping; browser security headers; ignored secrets and local-only runtime artifacts.

Demo role entry is intentionally open for judges and isolated to the sample demo school. Sandbox uses a private administrator password and invitations for parents. Sandbox role selection by the same administrator password is a hackathon operator control, **not** independent production finance identity. Before real school use, replace it with an identity provider, MFA and separately provisioned memberships; remove shared-password finance entry; disable public demo entry; add database row-level tenant policies as defense in depth; secure backups, retention, audit tamper resistance, incident response and operational monitoring.

Teacher/admin projections never include aid recipients or family obligations. Finance service APIs enforce authorization even when routes/UI are bypassed. Studio sources and exports contain aggregate financial values and status counts only. The focused agent has only aggregate-summary and validated report-presentation tools, with a five-turn cap. It has no financial mutation tools. Parent and quote AI calls exclude aid allocations. A document or message is untrusted content, never a source of system instructions or authorization. No confidence score controls assistance or money. Financial report titles/layouts are presentation state only.

Single-use invitations use 256-bit random tokens, SHA-256 hashes, short expiry and transaction-locked consumption. Link possession grants that sample family session; share invitations privately. WhatsApp links require verified pairing of the phone from the authenticated portal and an inbound exact code from that phone. Prompt text cannot authorize consent or payment.

Known boundaries for next pass: stronger CSP compatible with vendor runtime styles, upload antivirus/PDF sanitization and stricter structural parsing; provider error edge cases; constant-time auth credential storage via a proper password hash/IdP; outbound reminder duplicate-click claims; quota retention cleanup; session/invitation retention cleanup; custom Studio state schema/size hardening; free-host cold-start resilience; accessibility audit of modal focus handling; and a full adversarial authorization audit. State-changing routes reject GET. Rate-limit IP headers are trusted only behind a configured proxy in production.

Never add real student or hardship records to this demo. It is not escrow, a charitable trust, or a nonprofit processor. No secret may be committed. AG Studio's client licence is intentionally delivered to authenticated browser users as required by the vendor; it is not an API credential and does not grant a separate Enterprise Grid licence.

## Financial closure controls

PayPal authentication receives the complete original event before business parsing. Streamed byte bounds, validated transport headers, finite timestamp/replay checks, full-event identity hashes and token-owned expiring inbox leases reject unsigned/colliding events and retain failed notifications. Identical authenticated retries are acknowledged without duplicate effects. No webhook body, buyer approval URL or raw provider error is committed to evidence.

The hosted receiver returns retryable 503 for verification API outages, unknown financial event types, unmatched operations, active competing leases or readback failures. A financial 2xx requires awaited ledger reconciliation plus durable inbox completion/audit evidence; there is no fire-and-forget work. The audit contains fingerprints and internal operation association, not payloads or buyer data. Original event integrity and signature acceptance were demonstrated with genuine signed sandbox approval/capture/refund events; mocks cannot close this gate. Cold starts can exceed provider request timeouts, so PayPal retries/resend and operator investigation remain necessary. See `HOSTED_WEBHOOK_VERIFICATION.md` for actual proof and remaining operational limits.

Irreversible capture claims and version compare-and-swap updates prevent stale readbacks from granting another mutation. Refund identities, row-locked balance reservations, independent readback and custom-ID recovery protect partial/full refunds across process crashes. Missing fees remain explicit accounting uncertainty; demo provenance cannot enter sandbox funding. School contributions require finance authorization, a treasury reference and an atomic audit entry. The ledger records attestations, not bank verification; production audit integrity and independent treasury controls remain release prerequisites.

The optional CE_TEST_SCHEMA connection setting is accepted only under NODE_ENV=test with a restricted ce_verify_ schema name. The independent-worker harness creates and removes only its isolated schema in the existing dedicated database; its provider adapter accepts only a loopback fake URL. It cannot invoke real PayPal order creation. Production never enables this test seam.

During the earlier financial-closure phase, the user explicitly authorized the one-dollar sandbox lifecycle and confirmed human checkout approval. Verification reconciled the already-completed capture, performed the duplicate-request safety check and issued one full refund through the finance-authorized application endpoint. Independent provider readbacks and aggregate Studio rendering are recorded without provider identifiers, approval URLs or credentials. No buyer login/password/approval was automated; no additional financial test or live payment is implied.

Hosted financial closure: the separately authorized Morgan USD 1 sandbox capture, duplicate-request check and one full refund are complete. Genuine signed approval/capture/refund callbacks matched the operation and provider readback; actual event resends left the REFUNDED ledger unchanged. Studio displayed USD 0.54 retained fees and −USD 0.54 net. The earlier transaction is unchanged. See [hosted verification](HOSTED_WEBHOOK_VERIFICATION.md) and the redacted lifecycle/redelivery evidence; no simulator or live payment is involved.

## Release audit

Gitleaks and a targeted all-ref blob audit found no committed credentials, checkout URLs, raw webhook signatures or payloads, buyer personal information, archives or browser sessions. A historical internal sandbox operation UUID was replaced with a fingerprint in the release source. The UUID identifies an application record and cannot authorize lookup or mutation. Fictional seed identifiers and example addresses are intentionally part of the application. The dependency audit reported 14 moderate development-tool findings and zero runtime findings.

The hosted test observed origin enforcement, secure cookies, tenant and role checks, unsigned PayPal and Twilio rejection, and the public Gemini restriction. The free service showed a cold-start interstitial before readiness. The database currently allows external TLS connections from any IP with authentication. Use the private same-region connection for the web service and review narrowing external access before production use.
