# Security and privacy

This is a synthetic-data hackathon MVP, not a production school information system.

Implemented: opaque random database-backed 8-hour sessions, hashed tokens at rest, HttpOnly/SameSite=Lax cookies and Secure on configured HTTPS; exact-origin CSRF enforcement on browser mutations; PostgreSQL tenant/object checks; separate finance role for individual aid records; parent ownership checks; Zod input limits; serialized trip freeze/registration via row locks; immutable financial obligations; unique logical payment/refund identities; provider signature verification and webhook inbox deduplication; durable per-hour request quotas; max-size and file-magic validation for quote uploads; no uploaded document persistence; no raw provider secret errors in UI/logs; CSV formula escaping; browser security headers; ignored secrets and local-only runtime artifacts.

Demo role entry is intentionally open for judges and isolated to the synthetic demo school. Sandbox uses a private administrator password and invitations for parents. Sandbox role selection by the same administrator password is a hackathon operator control, **not** independent production finance identity. Before real school use, replace it with an identity provider, MFA and separately provisioned memberships; remove shared-password finance entry; disable public demo entry; add database row-level tenant policies as defense in depth; secure backups, retention, audit tamper resistance, incident response and operational monitoring.

Teacher/admin projections never include aid recipients or family obligations. Finance service APIs enforce authorization even when routes/UI are bypassed. Studio sources and exports contain aggregate financial values and status counts only. The focused agent has only aggregate-summary and validated report-presentation tools, with a five-turn cap. It has no financial mutation tools. Parent and quote AI calls exclude aid allocations. A document or message is untrusted content, never a source of system instructions or authorization. No confidence score controls assistance or money. Financial report titles/layouts are presentation state only.

Single-use invitations use 256-bit random tokens, SHA-256 hashes, short expiry and transaction-locked consumption. Link possession grants that synthetic family session; share invitations privately. WhatsApp links require verified pairing of the phone from the authenticated portal and an inbound exact code from that phone. Prompt text cannot authorize consent or payment.

Known boundaries for next pass: stronger CSP compatible with vendor runtime styles, upload antivirus/PDF sanitization and stricter structural parsing; provider error edge cases; constant-time auth credential storage via a proper password hash/IdP; genuine remote webhook delivery; outbound reminder duplicate-click claims; quota retention cleanup; session/invitation retention cleanup; custom Studio state schema/size hardening; free-host cold-start resilience; accessibility audit of modal focus handling; and a full adversarial authorization audit. State-changing routes reject GET. Rate-limit IP headers are trusted only behind a configured proxy in production.

Never add real student or hardship records to this demo. It is not escrow, a charitable trust, or a nonprofit processor. No secret may be committed. AG Studio's client licence is intentionally delivered to authenticated browser users as required by the vendor; it is not an API credential and does not grant a separate Enterprise Grid licence.

## Financial closure controls

PayPal authentication receives the complete original event before business parsing. Streamed byte bounds, validated transport headers, finite timestamp/replay checks, full-event identity hashes and token-owned expiring inbox leases reject unsigned/colliding events and retain failed notifications. Identical authenticated retries are acknowledged without duplicate effects. No webhook body, buyer approval URL or raw provider error is committed to evidence.

Irreversible capture claims and version compare-and-swap updates prevent stale readbacks from granting another mutation. Refund identities, row-locked balance reservations, independent readback and custom-ID recovery protect partial/full refunds across process crashes. Missing fees remain explicit accounting uncertainty; demo provenance cannot enter sandbox funding. School contributions require finance authorization, a treasury reference and an atomic audit entry. The ledger records attestations, not bank verification; production audit integrity and independent treasury controls remain release prerequisites.

The optional CE_TEST_SCHEMA connection setting is accepted only under NODE_ENV=test with a restricted ce_verify_ schema name. The independent-worker harness creates and removes only its isolated schema in the existing dedicated database; its provider adapter accepts only a loopback fake URL. It cannot invoke real PayPal order creation. Production never enables this test seam.

The user explicitly authorized the one-dollar sandbox lifecycle and confirmed human checkout approval. Verification reconciled the already-completed capture, performed the duplicate-request safety check and issued one full refund through the finance-authorized application endpoint. Independent provider readbacks and aggregate Studio rendering are recorded without provider identifiers, approval URLs or credentials. No buyer login/password/approval was automated; no additional financial test or live payment is implied.
